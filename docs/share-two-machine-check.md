# 分享：两台真机验证清单

到目前为止，分享的全部验证都跑在**单机双 endpoint** 上。那能证明协议对，证明不了
真实网络。下面这些事只有真开两台 Mac 才验得到，而它们恰好是会议室里最容易翻车的。

每一项都写了「该看到什么」和「不对时看哪里」——分享的失败大多是安静的，两边日志
都显示正常，所以要知道往哪看。

> 单机能先跑的两样，跑完再上真机：`cargo nextest run -p vt-ffi -E
> 'binary(share_ux_end_to_end)'` 走完整场 UX 叙事；
> `bash scripts/share_relay_smoke.sh` 对**已部署的** invite/relay 服务验证
> 「邀请码 → 登记 → 中继放行 + 陌生人被拒」。这两样绿了，真机清单剩下的
> 才是纯网络问题。

## 准备

两台 Mac，都装当前构建。任选一台当主持人。

主持人：**分享**标签页 → 「从这台 Mac 分享」→ 选内容与权限 → 开始共享 → 复制分享码。
另一台：**分享**标签页 → 「加入别人的」→ 粘贴分享码（回车即加入）。

---

## 一、同一 Wi-Fi（最常见的场景）

**做什么**：两台连同一个 Wi-Fi。主持人开始录音，说几句话。

**该看到**：另一台的分享页出现实时字幕，和主持人自己屏幕上的几乎同时——延迟应当
感觉不到，因为局域网直连是亚毫秒级，端到端延迟基本全来自 STT 出字。

**分享页应当显示「直连」**（绿色闪电图标）。显示「经中继」说明直连没打通，多半是
下一条。

**不对时看哪里**：
- 完全没有字幕 → 先确认主持人**真的在录音**。分享传的是采集的实时预览，没在录音
  就没有源。
- 有字幕但显示「经中继」→ 这个 Wi-Fi 大概率开了**客户端隔离**（AP isolation），
  见下一条。

## 二、AP 隔离（会议室 / 酒店 / 咖啡馆的常态）

很多公共 Wi-Fi 禁止同网段的设备互相通信。这时直连和 mDNS 会**双双失效**。

**怎么确认**：在两台机器上互 ping 对方的局域网地址。ping 不通就是开了隔离。

**该看到**：分享**仍然可用**，但状态显示「经中继」。这条路径需要互联网——中继在
`zulangue-relay.exe.xyz`。

**不对时看哪里**：
- 完全连不上 → 检查设置 › 分享里的中继地址是不是空的。空表示只走直连，在这种
  网络下就没有出路。
- 中继地址填了还是连不上 → 这台机器的 endpoint 可能没在邀请码服务登记过。中继
  只放行登记过的 endpoint。

## 三、本地网络权限（macOS 15+）

**做什么**：在一台**从没用过分享**的 Mac 上首次加入。

**该看到**：macOS 弹出「允许 Zulangue 查找并连接本地网络设备」。

**然后故意点拒绝**，再试一次加入。

**该看到**：分享码**照样能用**。分享码里内嵌了直连地址，不依赖 mDNS。拒绝只是让
「自动发现同一网络的人」失效，不该让整个功能失效。

**不对时看哪里**：拒绝后完全连不上，说明代码把 mDNS 当成了必需路径而不是加速路径。

## 四、CGNAT 回落（跨网络）

**做什么**：一台连 Wi-Fi，另一台连 **iPhone 热点**。这模拟两人不在同一个网络。

运营商的 CGNAT 会让打洞经常失败，中继是唯一出路。

**该看到**：能连上，状态显示「经中继」。字幕延迟会比局域网明显——多了一跳到新加坡。

**不对时看哪里**：
```bash
# 中继有没有拒绝这台机器
ssh zulangue-relay.exe.xyz 'sudo journalctl -u zulangue-share-relay --since "5 min ago" | grep -i "access check"'
```
注意「正文不是 true」这条消息对**拒绝**和**故障**是同一句。要分辨，看已登记的
endpoint 有没有出现 `access check OK`。

## 五、文档协同

**做什么**：两台都在同一个共享 Notebook 里编辑笔记。

**该看到**：改动双向同步。**转录稿里录音拥有的那一段改不动**——这是设计如此，
采集投影拥有的区间不接受远端改动。

**再试**：主持人把权限设成「主持人可写、其他人只读」，让另一台去改。

**该看到**：改不进去。注意这个保证的真实形状——它靠每台机器自己过滤，不是发送端
强制。改过客户端的人能在自己那份上随便改，但诚实的机器会丢弃。

## 六、停止共享

**做什么**：主持人点「停止共享」。

**该看到**：另一台不再收到新字幕，但**已经收到的内容还在**。界面上那句说明就是这个
意思——停止只停后续，删不掉对方已有的。这不是 bug。

**还该看到**：观看端的状态条几秒内变成「主持人结束了这次共享」（灰色斜杠电波
图标），不在分享页时会弹一条同文案的 Toast。停在「Receiving captions」不动 =
Goodbye 没送达，看 gossip 是不是早就断了。

## 七、录音条上的共享指示器（主持人机器）

**做什么**：主持人共享整本 Notebook，开始录音。

**该看到**：采集工具条与菜单栏录音 popover 上出现琥珀色「正在共享字幕」+
「这段不共享」按钮；全屏 REC 药丸上多一粒琥珀电波。点「这段不共享」后，
另一台的字幕**立刻停**，指示器变灰；「恢复」后再来。

**再试**：切到**另一本** Notebook 录音。

**该看到**：指示器不亮，另一台也收不到字幕——共享范围只覆盖选中的那本。

## 八、敲门的全局提醒（主持人不在分享页）

**做什么**：主持人切到采集页或其它标签页；另一台在「加入别人的」道里等自动
扫描找到主持人（约十秒内），点「请求加入」。

**该看到**：主持人这边弹 Toast「××× 想加入你的共享」，侧边栏「分享」项挂上
数字角标。到分享页批准后，请求方自动进房。请求方那行显示「等待回答…」和
「不等了」——点「不等了」界面立刻解锁。

## 九、收件的删除

**做什么**：观看端收到单条录音的副本后，先在房间里对收件行右键。

**该看到**：「从这台 Mac 删除」是**禁用**的——当前房间那条删了会被同步拉回来，
所以先离开房间。离开后再右键删除（有确认框），列表里那条消失，重进分享页也
不再出现。

## 十、主持人侧的链路徽章

**做什么**：房间建立后看主持人的成员列表。

**该看到**：每个观看者名字旁有绿色闪电（直连）或琥珀色天线（经中继）。
「所有人都是琥珀色」就是第二条说的 AP 隔离——这个判断现在主持人自己就能做，
不用去问观看端。

## 顺手看一眼运营统计

跑完以上，中继应当记下了流量：

```bash
ssh zulangue-invite.exe.xyz 'cd ~/zulangue-community-invite && python3 -c "
import sqlite3; db=sqlite3.connect(\"data/invites.db\"); db.row_factory=sqlite3.Row
for r in db.execute(\"SELECT * FROM relay_daily ORDER BY day DESC LIMIT 3\"): print(dict(r))
"'
```

只该看到聚合量。**看不到「谁连了谁」——那个数据不存在**，不是被隐藏了。
