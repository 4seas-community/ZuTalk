# 多语言实时转写与翻译：哪些是通用的，哪些按语言

泰、中、英三语一起录时，问题出在哪一层：是某种语言要特殊处理，还是通用模块本身有毛病。本文是 2026-10 一轮完整测试的结论，也是以后改这一块之前该先看的清单。车道、时间线和落行的总体设计见 `timeline-projection.md`；录音页和字幕浮窗见 `live-presentation.md`。

## 车道结构随语言组合而变

`remote_stream_plan` 按所选语言决定开几条连接：

- 一种语言：只有主车道，只转写。
- 两种语言：一条双向连接，同时是主车道；原文和译文在同一条流里，没有跨车道落行。
- 三种及以上：主车道是一条单向连接，译成所选列表里**最后一种**（有只看字幕的语言时译成它）；其余每种语言各开一条单向辅助车道。辅助车道的译文按时间落到主车道的行上。

所以「语言组合」首先改变的是结构：只有三语模式有跨车道落行，也只有三语模式会遇到车道之间时间对不上的问题。选择顺序决定谁走主车道。

实测（同一份素材，真 Soniox）：

- 三语三种顺序（主车道分别译成英、中、泰）表现一致：译文栏填满率、延迟、车道时钟偏差都没有差别。
- 双语三组（泰英、中英、泰⇄中）和三语一样快：说完到定稿中位 0.4–0.7 s，停止 0.5–0.6 s。早先几轮泰⇄中慢约 1 s、停止要 3 s，看上去像这一对语言的问题；其实泰语一侧各组都慢（泰英也到过 1.7 s），慢在长泰语句要等服务商自己断句。主车道在 200 ms 静音处收尾以后就不慢了，所以不需要为泰⇄中改成两条单向连接（那样连接数和费用翻倍）。

## 通用模块：与语言无关

以下问题对每种语言、每条车道都一样，只是泰语因为词元碎、句子长，往往最先暴露。

1. **车道时钟。** Soniox 每次 finalize 都把自己的时钟往前推约 100 ms，之后所有时间戳都带着这段时间。辅助车道在主车道每次断句时都会收到一次 finalize，九分钟对话累计晚 4–5 s，短句的译文因此落到下一个说话人的行上。服务商回应 finalize 时报告的处理量减去发 finalize 时已送出的音频，就是它加进去的时间；`StreamRecoveryState::capture_ms` 把它扣回（vt-stt）。服务商按顺序回应 finalize，但偶尔会漏掉一次（改回 `<end>`，或干脆不回）。所以 `<fin>` 仍按先进先出配对，只有回应落在最早那次之后超过 1 s（一次 finalize 只加约 0.1 s）时，才认定那次被漏掉、跳过去；否则一次漏回就会把两次之间的音频算成服务商加的时间，之后的时间戳整体提前十几秒。也不能干脆配「服务商已听到的最晚那次」：辅助车道常在几十毫秒内连收两次 finalize，服务商两次都回，那样配会让第一个回应占掉第二次，每对少算 0.1 s，越录越早。
2. **长句收尾。** 服务商的断句要等比人在句间留的更长的停顿，独白会一直拖到 25 s 上限、切在句中。主车道一句超过 10 s，就在音频真的静音 200 ms 处 finalize（`LongUtteranceCloser`，配置 `close_long_utterances_at_pauses`，只给主车道开）；辅助车道随主车道的边界一起收尾，原文和译文切在同一段静音里。**不能按「一段时间没有新词」判断停顿**：服务商常常晚吐一个词，在那时 finalize 会把这个词丢掉——实测长泰语每个切点前都丢一个音节（ดาดฟ้า 只剩 ดาด）。25 s 上限保留。收尾器不能无限等回应：服务商听过 finalize 的位置 1.5 s 还没有 `<fin>` 或 `<end>`，就当这次丢了，下一个停顿可以再发；服务商整体停住（网络卡）时只是晚到，继续等，不连发。下一句从服务商实际断句的位置算起，不从收到回应那一刻已送出的音频算起：服务商落后几秒时，后者会让每一行多拖几秒才能收尾。实测这几处以前合起来让最长行在各轮之间从 14.5 s 到 20 s 以上不等。
3. **切行。** 说话人和语言同时变，一定另起一行（真换人时停顿最短只有 60 ms）。只换说话人标签、没换语言，要停顿至少 200 ms 才另起：服务商的说话人标签会在词中间翻转（泰语 เต็น|ท์、英语 fin|e.）。服务商把一个英文词拆成几个词元，新词一律带前导空格；紧跟拉丁字母、自己又以拉丁字母开头的词元是上一个词的后半截，不另起一行，也不算一个新词（同一个人，或者标签翻转但没有停顿）。以前「Hotsp|ot」「Of cours|e.」被切在两行，后半行开头是半个词，译文对不上。服务商断句时还没定稿的词是断句另一侧的推测，连接还在，下一批会重发：只有推测的段丢掉，挂在已定稿行后面、说话人或语言对不上的推测尾巴也丢掉，不冻结成一行。以前尾巴被冻结，撤回时存储层用辅助车道的同语言证据补成一个壳，页面上「Of cours」和「Of course.」并排两行（只在三语出现）。重连、停止时照旧冻结，那时没有下一批。
4. **落行。**
   - 重叠按译文段自身的音频算：哪一行占了它大部分音频就归哪一行。
   - 录音中只落到占一半以上、或有文字证据的行；不够的等结算。
   - 段修订后，所在栏未定稿时可以换到更合适的行；离开的行作为更新发出，不报成删除。
   - 和任何行都不重叠、但相距不到 400 ms 的段，落到最近的那一行，那一行还在说也行。一个词的回答（Perfect.、Thanks.）在辅助车道上只有几十毫秒，车道之间对同一个词的时间又差一两百毫秒，以前会退到两行以前。
   - 仍保留的局限：两边断句不一致时，一段译文整段落到占多数的那一行，邻行这一栏会空（实测约百分之一的栏）。
5. **行改语言。** 一行的语言可以在挂上译文之后才改：句首一两个拉丁字母的词跟着后面那句走、按文字定语言，都会把行改成别的语言。双语模式里原文和译文在同一条流上，服务商会把行首那个词译成另一种语言——中英双语里「上次」被听成英文「Shots」、译成中文「开枪」，同一个人紧接着说中文，这一行就成了中文行，手里还拿着一段中文「译文」。两处规则：行变成译文缓冲的语言时，清掉缓冲（`apply_original_token`），那不是这一行的译文；存储层改原文语言时已经删掉占着新语言的译文栏，写入时不再去撤回它（`persist_assembled_utterances`）。以前这次撤回会被当成「译文和原文同语言」拒绝，报成 `local_persistence`，整条连接在第 8 秒停掉。

## 按语言的规则：集中在这几处

| 位置 | 规则 | 原因 |
|---|---|---|
| `vt_model::text::normalize_provider_text` | 泰文 ำ 合成为 U+0E33；中日文全角标点两侧的空格去掉，汉字之间的空格保留 | Soniox 一律给分解写法；汉字间的空格常是它代替标点 |
| `vt_model::text::polish_translation` | 从以空格分词的语言译成中日文：去掉汉字之间的接缝空格；从泰语译成中文：保留。译成泰文：去掉 ค่ะ、คะ、ครับ | 前者是流式译文分块拼接的接缝；后者替说话人猜了性别，原话里没有 |
| `vt_model::script::language_written_in` | 字母全在一种非拉丁文字里、而所选语言只有一种用它时，按文字定语言 | 服务商会把泰文标成英文，整行进了英文栏。拉丁字母不算：它常是夹在泰语、中文里的英文词 |
| 组装器 `source_segment_for_token` | 泰语、中文句子里，同一个人夹一两个拉丁字母的词（停顿不到 0.7 s）不另起一行；第三个词才算换了语言（按词数，不按词元），这时前面那一两个词是新句子的开头，跟着搬到新行（服务商把两个人标成同一个说话人时，「…4 ทุ่ม If you / are joining…」）。行首一两个拉丁字母的词后面紧接泰文或汉字，这一行归后面那句的语言，但已经以句号、问号、叹号结束、后面又停了至少 200 ms 的（「Of course.」，别人的回答）是自己的一句，不跟；服务商给加了句号却紧接着往下说的（「上次」听成「Shots.」）照样跟；数字、标点不带语言 | 否则一个英文术语就把句子切开，切出的单词行没有译文 |
| store `adopt_translation_inbox_source_language` | 已定稿的行，文字里一个该语言的字都没有、而辅助车道听成了文字所属的语言，就改标签 | 标错的行吞掉了译成它标签语言的那段译文 |
| `vt-store` 搜索 | 不用空格分词的文字（泰、老挝、缅甸、高棉、中日、韩）走子串匹配，并兼查 ำ 的分解写法 | FTS5 unicode61 在泰文组合符处切词 |
| 字幕显现 `CaptionScriptProfile` | 泰文按词（CFStringTokenizer）、中日文按字、其余按空格分词，各有速率 | 泰文不能按字形拆，否则元音、声调符号会和辅音分开 |

## 已知、未修

- **句中夹外语术语识别差**：DAO 听成「导游」，hackathon 听成「podcast」，泰语里的 open source 听成「พื้นโซฟา」。部分是合成语音念外语词的问题，但这是三语场景的真实弱点。笔记本挂术语包（22 个词：活动名、地名、人名、产品名）之后，同一份夹术语的素材识别错误率泰语 17.7% → 11.6%、英语 17.8% → 15.1%、中文 29.5% → 25.8%，译文栏填满率和延迟不变。术语多的场合值得挂。
- **服务商的个别译文**：中译英偶有语法不通的句子（「You average to wait several seconds…」）。
- **不换气的长独白**：说话的人十几秒不留 200 ms 的停顿，这一行就收不了尾（合成泰语独白最长到过 22.4 s）。没有丢词，译文栏照样填满；25 s 上限照旧。门槛降到 100 ms 会切在词与词之间，不降。
- **网络卡顿时现场丢转写**：服务商落后 15 s 时车道切断重连、跳到直播沿，跳过的那段现场没有字（实测一次 15 s、一次 31 s，三条车道同时）。音频在本机日志里都在：开了录后整场转写、用自己密钥的人，停止后整场重转一遍，空洞会补上；只用邀请额度的人走不了这一步（邀请只覆盖实时转写），记录里就缺这一段。

## 怎样复测

```
python3 scripts/multilingual/make_suite.py <素材目录>
ZUTALK_INVITE_TOKEN=<邀请文件> bash scripts/multilingual/run_matrix.sh <素材目录> <输出目录>
```

素材由 macOS 合成语音按固定脚本生成，逐字节可重现：快速轮流发言、夹术语和数字、长独白、快语速、嘈杂（人声、粉红噪声、混响、变调），以及给矩阵用的 core 和三组双语素材。`run_matrix.sh` 依次跑六组配置（三语三种顺序、三组双语），每组记录回调、车道追踪和逐段对照，分数写进 `summary.txt`：译文栏填满率、识别错误率（按文字对齐脚本段落）、主车道和脚本的时间差、行长、跨段的译文段、延迟、中文接缝空格和泰语语气词。

车道追踪只在 debug 构建里、设了 `ZUTALK_LANE_TRACE` 时写：每条车道的每个服务商事件，以及服务商时钟和已送出音频的对照。`scripts/multilingual/trace_offset.py` 逐词对齐主车道和辅助车道的原文，给出时钟偏差随时间的变化。
