# 网页分享：扫码看实时字幕稿

分享页的第二条出口。P2P 分享（[share-p2p.md](share-p2p.md)）要求对方也装着
ZuTalk；网页分享面向**没装应用的人**：主持人开启后得到一个二维码和链接，
扫码进入网页就能看实时字幕，多语言转录可以切换语言，落定的内容累积成稿。

定案时间 2026-08-09。

## 0. 与 P2P 分享的边界

| | P2P 分享 | 网页分享 |
| --- | --- | --- |
| 对方需要什么 | ZuTalk 应用 | 任何浏览器 |
| 传输 | iroh 端到端加密 | HTTPS 经 `caption-web` 服务 |
| 服务器可见性 | 看不到明文 | **看得到明文**（见下） |
| 协同订正 | 有 | 无（只读网页） |
| 内容留存 | 收端落库 | 服务器保存,留存期满即清（默认 24 小时,见 §2） |

**明文取舍是用户明示的决定（2026-08-09）**：网页分享开启后，字幕明文经过
服务器。备选的端到端方案（密钥放 URL 片段、浏览器端解密、服务器只存密文）
被评估过、暂不实施——代价是网页端复杂度与调试难度。两条界限必须守住：

1. **UI 必须说出这句话**。开启网页分享的确认界面上写明「字幕明文会经过
   服务器，并在分享结束后继续保留一段时间」，不得含糊。App 说「一段时间」
   而不说小时数——留存期是服务端的配置;观看页从 `init` 拿到确切窗口,
   自己说清「这个链接还能开多久」。P2P 分享的隐私叙述不适用于这条通道。
2. **音频照旧结构性排除**。网页通道只承载与 P2P 字幕通道相同的纯文本类型
   （`CaptionFrame` 与块快照），四层音频门禁（share-p2p.md §5）原样生效。

## 1. 架构

```
主持人 App                      caption-web (exe.xyz)            浏览器
─────────────                  ────────────────────            ──────
ShareCaptionTap ──帧──►  POST /v1/rooms/{id}/frame  ──SSE──►  实时 tail
publish_shared_session         POST /v1/rooms/{id}/blocks ──►  字幕稿
  └─块快照(去抖)──►
stop_sharing ────────►   DELETE /v1/rooms/{id}      ──SSE──►  「已结束」
```

- **帧**：与 P2P 同一份 `CaptionFrame`（完整形态：utterance/cue/lane 健康），
  replace-in-full，网页端整帧替换,丢帧无害。**必须经 `ShareCaptionTap` 的
  同一放行判定**（范围过滤、per-session 静音）——P2P 不发的帧,网页也不发,
  不存在第二套判定。
- **分割线（segment）**：录音的开始/暂停。帧与稿都是 replace-in-full 的
  **状态**,而「暂停过一次」在状态里没有痕迹——帧只是不再来了。所以它
  单独走一条**追加式**通道(顺序即语义,不能被新值覆盖),带一次重试:
  漏一帧无所谓(下一帧带着全部真相),漏一条线就永久少一条。放行判定
  与字幕同源——静音或范围外的录音一条线都不留,一条承诺了内容却永远
  不来的「录音开始」比没有线更坏。暂停时服务端顺带清掉存着的最新帧,
  否则暂停期间扫码的人会看到一句停在半空的推测文本。
- **块快照**：字幕稿的来源。宿主本来就为共享 session 维护 T2 块文档
  （share-p2p.md §11）,`publish_shared_session` 时顺带把块列表
  （text + 各语言车道）推给服务,replace-in-full,服务端只留最新。
  网页的「稿」= 块快照;「实时」= 帧。两个时态,与 App 收端一致。
- **推送不阻塞采集**：帧进 tokio `watch` 通道（新值覆盖旧值——
  replace-in-full 的天然搭配）;块**按 session 覆盖后排队**——稿的
  「只留最新」是每个 session 一份,不是全局一份（§3）。独立任务用 reqwest
  慢慢发,发不动就丢中间态,与 P2P 扇出同一哲学（share-p2p.md §3.3）。
- **订阅**：网页用 SSE（`EventSource`）。单向、自动重连、纯 HTTP,
  stdlib `ThreadingHTTPServer` 一条长连接一个线程就够——观众是会议室量级,
  不是直播量级。

## 2. 服务:services/caption-web

与 `community-invite` 同一形态:Python 标准库单文件、systemd 托管、
用户自己部署。默认部署位 `https://zutalk-caption.exe.xyz`。

### 接口

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/v1/rooms` | 无（见滥用上限） | 建房,返回 `{room_id, publish_token, viewer_url}` |
| POST | `/v1/rooms/{id}/frame` | Bearer publish_token | 最新一帧,fanout |
| POST | `/v1/rooms/{id}/blocks` | Bearer publish_token | 最新块快照,fanout |
| DELETE | `/v1/rooms/{id}` | Bearer publish_token | 封笔,订阅者收 `ended`;稿留下 |
| GET | `/v1/rooms/{id}/events` | 无（room_id 即门票） | SSE:先发全量（blocks+frame+留存期）,再发增量;已封笔的房间发完全量直接给 `ended` |
| GET | `/r/{id}` | 无 | 观看页（内联 HTML/JS,无外部依赖） |
| GET | `/healthz` | 无 | 探活 |

`room_id` 与 `publish_token` 都是 `secrets.token_urlsafe`——房间号即门票,
不可猜测;发布口令只有主持人持有。

### 状态与留存（2026-08-10 修订）

留存规则只有一条,其余都由它推出:**稿从最后一次推送起活 24 小时**
（`--retention-hours` 可改),到点由清扫线程删掉,盘上那份一并消失。

- **停止共享是封笔,不是删除。** DELETE 之后房间拒收推送、在线的人收到
  `ended`、推测性的最后一帧被清掉,但稿留着,链接照样打得开。散场恰恰是
  最多人去读稿的时候;删房等于把「扫码看字幕」缩成「必须现场看完」,而
  提前删并不改变明文经过服务器这件事,只让来晚的人白扫一次码。
- **重启不作废链接。** 配 `--state-file` 就把房间身份、稿、分割线落一份
  盘（0600,原子替换,去抖写);**帧不落盘**——它是推测性的半句话,重启后
  要么主播再推一份,要么本来就该消失。

  初版写的是「内存态,不落盘;进程重启即空」,并把它当成一条隐私保证。
  它不是:明文本来就要在这台机器上待满整个留存期,重启清空并不让谁更
  安全,只是让**恰好那一刻**手里拿着链接的人白拿——一次部署、一次 OOM、
  一次 systemd 重启,会场里所有二维码同时作废,而会还在开。真正的保证是
  留存期本身,加上把这件事说清楚(见下)。
- **UI 必须跟着说。** §0 那条「UI 必须说出这句话」现在多一句:字幕不只
  经过服务器,还会在结束后继续留一段时间。App 说「一段时间」不说小时数
  ——留存期是服务端的配置;观看页从 `init` 里拿到确切窗口,自己说清
  「这个链接还能开多久」。
- 房间数上限、载荷字节上限、建房按 IP 限速——挡的是脚本滥用,
  不是「未授权用户用不了」。

### 延后项

- **建房接邀请码门禁**:与 relay 门禁同构（endpoint 登记 + ed25519 签名
  验证）,滥用真出现了再立;
- 端到端加密选项（密钥进 URL 片段）。

## 3. App 侧

### Rust（vt-ffi/src/share_web.rs）

`WebShareRuntime` 挂在 `ShareRuntime` 里（web 分享是「当前这场共享」的
属性,随 `stop_sharing` 一起收口）:

- `start_web_share()`:仅主持中可开;POST /v1/rooms,起推送任务,
  **并把范围内每一场录音的稿各推一份**;
- `stop_web_share()`:DELETE(尽力而为,fire-and-forget)+ 停任务;
- `web_share_state()`:给 UI 的快照(viewer_url 等);
- 帧入口在 `ShareCaptionTap::broadcast` 放行之后——同一帧、同一判定;
- 块入口在 `publish_shared_session`——宿主每次发布 P2P 更新时,
  同一份块列表推给网页(按 session 覆盖 + 任务端去抖)。

**开房要把范围内的稿推全,不能等下一次发布。** 服务端给每个新订阅者重放
全部块快照,所以只要稿到过服务端,几点扫码进来的人都从头看得到;反过来,
没推过的 session 在它下一次真有增量之前,网页上就是不存在。一场会议的
前半段往往早就录完、再也不会有增量,「随下一次发布补上」等于永远不补。

**待发的稿按 session 覆盖,不是单槽。** 稿的 replace-in-full 是「每个
session 只留最新」,不是「全局只留最新」——单槽 `watch` 会让开房时连着
推的几场只活下来最后一场。所以槽位是个有序表:同 session 原地覆盖
(位置不变,推送先后就是网页上的先后),不同 session 各占一格,推送任务
整批取走再发。

**说话人不在 T2 文档里。** 块只有 id/owner/text/lanes,说话人是 SQLite
采集行上的事实。块 id 就是 utterance id,`push_web_share_blocks` 查一次
`list_utterances` 把两边接上,再按 `list_session_speakers` + 联系人表拼出
名录(取名规则与 App 画布一致:会话内改名 → 联系人名 → 只送 provider
编号)。转发别人的稿时查不到采集行,名录为空,网页退回不显示说话人 ——
缺名字不该让稿本身消失。

### Swift(分享页)

主持中的「网页分享」卡片:开启前一句确认(明文警示);开启后显示二维码
(CoreImage `CIQRCodeGenerator`,零新依赖)、链接(可选中可复制)、
停止按钮。停止共享时网页分享一并结束,UI 不单独残留。

## 4. 观看页

单文件内联 HTML/JS/CSS,无外部资源(会议室网络不可预设能访问 CDN):

- **界面文案三语**(简体中文 / ไทย / English):观看的人就是这三种语言
  背景,英文独占的「This share has ended」对另外两种人是谜语。按
  `navigator.language` 自动选,右上角可手动切并记进 localStorage;
  界面语言与内容语言按钮互相独立;
- 顶部语言按钮**多选,最多三栏**并排:从块车道与帧 cue/utterance 语言
  并集自动生成,外加一个「原文」伪语言(原文不在车道里,不造它就没法
  把原文当一栏)。第四个顶掉最旧的;栏是「已选 ∩ 本房间真有的」——
  上一场留在 localStorage 里的语言不该占一个取消不掉的空栏;
- **实时区按栏分流**:每栏只收自己语言的句子,原文栏只收本帧的主导源
  语言(按带说话人标识的句子判定,句数优先、长度只做平票裁决)。真实
  录音的帧里语言识别会飘、辅助车道有碎片,不分流就会全糊进第一栏越积
  越长。与稿的去重按子串(碎片常是已落稿句子的一部分),每栏只留最近
  几行;正在说的文字直接续在稿下原地刷新,不做引用块;
- 正文:落定块(选中语言的车道文本,**缺席回落原文**,弱一档颜色)
  + 实时 tail(推测性,弱色显示)。

  回落不是补白,是那一栏唯一正确的内容:原文本来就是中文时,系统不会
  再造一条「中文→中文」的车道,选中文的那一栏在稿里一格车道都没有。
  不回落,一场中文会议的中文栏整屏空着,译文栏反倒满满当当 —— 这正是
  2026-08-09 报上来的现象。同一条回落也管一句英文原话落进英文栏。
- **说话人**:块带 `speaker`(本场录音内的标识),块快照另带一份
  `speakers` 名录(标识 → `{name, label}`)。名字是用户给的(会话内改名
  或关联联系人)就原样显示 —— 那是专名,不翻译;只有 provider 编号时,
  「说话人 3」这句话由网页按观看者的界面语言拼,与页面其余文案同一条
  规矩。稿与实时帧用同一套标识,名录只有一份。
  显示成横跨全部栏的一条小标,**只在换人时出现** —— 同一句话在三栏里
  是同一个人说的,标三次是三份噪音;同一个人连说几句,标一次就够。
- 批注块横跨全部栏一行,不在各栏复制 —— 也不能只放原文栏,观看者可能
  一栏原文都没选,那条批注就凭空没了。
- 自动跟底,回滚即停跟,「回到实时」按钮;
- `ended` 事件后显示「这场分享已结束」,并说出这个链接还能开多久
  ——稿留在服务器上而不只是留在这一页里,读的人得知道该现在读完还是
  可以晚点回来。留存期从 `init` 里来;没拿到就退回不承诺时长的说法。
