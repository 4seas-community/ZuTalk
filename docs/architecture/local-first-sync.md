# 本地优先：设备之间直接同步（iroh）

定案 2026-09-29。负责人要求把 iroh 集成回来做本地优先，四项能力按顺序分期：

1. **自己的多台 Mac 同步**（本文第一期）
2. 和其他 ZuTalk 用户协作一个主题
3. 同一网络内直接共享（不经字幕服务器）
4. 加密备份到自己的另一台设备

**音频永远不同步。** 这是负责人的明确选择，不是默认值，没有开关。浏览器观众仍走加密链接
（[share-links.md](share-links.md)），iroh 只用于 ZuTalk 与 ZuTalk 之间。

## 0. 从现有存储推出来的几条硬约束

- **界面读的是 SQLite，不是 Loro。** 实时转录稿的句子、各语言栏、订正都在 SQLite
  （`realtime_utterances`、`_variants`、`_overrides`），T2 文档只是它的投影。只同步 Loro
  文档，另一台 Mac 上什么都看不到。
- **主题的三份文档编号每台 Mac 各自随机**（`notebook_tabs.doc_id`）。同名主题在两台 Mac
  上是两份不相干的文档。每场录音的笔记例外：编号由录音 id 推出，天然一致。
- **精修稿的用户编辑只存在 Loro 里**（主题的精修稿文档，按录音分段）。
- **「未归入主题」每台 Mac 各有一个随机 id**，靠保留标题找回。
- **没有变更日志。** 大部分表有 `updated_at`，`session_records` 等几张没有。
- 音频、音频密钥、「专有词与背景」资料的密钥都只在本机（`Secrets/content-keys.json`），
  路径是本机绝对路径。

## 1. 总体做法：同步事实，本地投影

同步的单位是 **Loro 文档**：CRDT 自带合并、版本向量与增量导出，上一代点对点已经验证过
「版本向量交换 → 导出差量 → 导入」这条路。分两类：

**A. 同步文档（新增，专为同步而设）**——SQLite 事实的可合并表示。收到后由「物化器」写回
SQLite，再由本机既有的投影流水线把它投进本机的 T2 文档：

- `library`（每个设备组一份）：
  - 主题：id、标题、建立时间、删除时间、三份文档的编号、录音设置（语言等）
  - 录音归属：录音 id → 主题 id（「未归入」记作空，各机映射到本机的那个）
  - 回收站状态：录音 id → 放入时间 / 空
  - 永久删除墓碑：录音 id → 删除时间（任何一台删了，所有设备都删）
  - 人名名单：id → 名字 / 删除时间
- `recording/<录音 id>`（每场录音一份）：
  - 元数据：建立时间、类型、状态、时长、语言、来源设备、来源信息（provider/model）
  - 标题（后写者胜）
  - 实时转录的**定稿**句子与各语言栏（只有录音那台写，写入即不变）
  - 订正：句子 × 语言 → 文字（后写者胜）
  - 说话人：标签、名字、关联的人名
  - 标记：时间范围、备注、删除时间
  - 精修结果（provider tokens，写入即不变）

**B. 直接同步的既有文档**——编号在设备组内一致，直接作为 CRDT 同步：

- 每场录音的笔记（编号由录音 id 推出）
- 主题笔记（编号随 `library` 里的主题一起定下）
- 主题的精修稿文档（同上）。**只有录音那台 Mac 投影它的精修段落**，其他设备只收不投，
  否则两台同时渲染同一段，合并后就是两份。

**不同步**：音频与音频密钥、录音中的实时预览、任务队列、云端转写的回收台账、共享链接台账、
设备本地的计数器与投影水位、「专有词与背景」（资料用本机密钥加密；第二期再定怎么带）、
各机的界面偏好。

## 2. 设备组与配对

- 每台 Mac 有一个设备身份（iroh `SecretKey`，存在 `Secrets/` 的本机密钥库里，键名
  `sync-device-identity`；它与音频的密钥无关）。
- 每台 Mac 生来就有一个只有自己的设备组（空间 id 随机 32 字节）。设备名单是一份同步文档
  `roster/<空间>`：设备 id → 名字，另有一张「已移除」表。**移除是永久的**：同一个设备 id
  之后再出现在名单里也不算成员，本机还在 `sync_removed_devices` 里另记一份。名单不做签名：
  只有名单上的设备连得进来（QUIC 已认证对方 id），能改名单的也就只有它们。
- 配对：在已有设备上点「生成配对码」，得到一个 10 分钟内有效、只能用一次的码（含已有设备的
  地址、一次性密钥和用途：加 Mac / 邀请协作主题 / 指定备份机）；新 Mac 上粘贴。新 Mac 出示
  由密钥推出、绑定双方设备 id 的证明，密钥本身不上线。
- 新 Mac 加入时换上对方的设备组；它自己的主题与录音原样留着，随后全部导出给新组。它原来的
  资料库文档（人名名单、墓碑）丢掉重建，免得旧组的东西混进新组。
- **「未归入主题」不同步它本身。** 每台 Mac 各有一个，录音文档里记作空，各机映射到本机的
  那个。原设想是加入时把录音挪进设备组的那一个，但两个保留标题的主题同时存在时，现有的
  两处查找会各挑一个；挪动还要合并两份不相干的精修稿文档。改为不同步之后的代价是：
  未归入主题里的录音，**手改过的精修稿不跨设备**——每台按同步来的精修结果各自渲染一份。
  录音本身、实时转录、订正、笔记、标记都照常同步；挪进某个主题之后精修稿也跟着同步。
- 移除设备：从名单上划掉，其他设备不再和它同步；它自己留着已经同步到的数据。

## 3. 传输

- iroh 1.3.0，`presets::Minimal`（不把地址发布到公共目录）；自建中继
  `zulangue-relay.exe.xyz`；同一网络用 mDNS 发现。
- 每对设备一条连接，所有文档复用：先交换各自的文档摘要（文档 id → 版本向量的哈希），
  只对不一致的文档交换版本向量与差量；本机改动实时推送；断线自动重连（在传输层，不靠界面
  轮询）；重连后先对摘要。
- 两边都会拨号：设备 id 小的一方先拨，大的一方等 3 秒没见到连接再拨（对方可能在退避，
  或还守着一条已断的旧连接）。两条连接建立时间相差不到 3 秒算同时拨出，两边都留 id 小的
  一方拨出的那条；否则新的换掉旧的——对方肯拨过来，说明它那头已经没有可用连接。
- 只拉不推：每台设备按对方的摘要要自己缺的，对方按请求方的版本导出差量。每个请求都有
  应答（没有可给的也回空的末块），反熵每 60 秒一轮完整摘要。
- 编码用 postcard，按文档分块，单块上限 1 MiB；一个大文档的追赶分多块发。
- 只接受名单内设备的连接（QUIC 已认证对方 id，直接对名单）。
- **中继门禁**：原来只放行登记过邀请码的设备，没有邀请码的人跨网络就同步不了。改为放行所有
  设备，靠中继自带的限流防滥用：每个客户端上行 256 KiB/s（可突发 4 MiB），每秒新连接
  20 个（可突发 100）。流量本就端到端加密，中继只转密文。第一次全量同步多半在同一网络里
  直连，中继只是跨网络时的后备，这个上限够用。

## 4. 冲突与删除

- 文字（笔记、精修稿、订正）：Loro 合并。
- 标量（标题、归属、回收站状态、名字）：后写者胜（Loro Map 的 Lamport 时序）。
- 永久删除：墓碑优先于一切——任何设备收到墓碑就执行本机的永久删除，之后再收到这场录音的
  任何内容都丢弃。
- 删除主题：录音移到「未归入主题」，主题标记删除；和单机行为一致。

## 5. 界面（第一期）

- 设置 › 设备：本机名字、已配对的 Mac（在线/上次同步时间）、添加 Mac、移除。
- 另一台 Mac 同步过来的录音不再显示「音频已删除」，而是「来自 X」；录音页的音频一栏写
  「在 X 上」，转录按钮换成「音频在 X 上，请在那台上转录」（核心也会拒绝，错误是稳定代码
  `sync.error.audio_elsewhere`，界面按代码查各语言的说法）。
- 录音行与录音页：来自另一台 Mac 的录音标注「在 X 上录的」；没有音频时，「精修转录」
  「导出音频」这类需要音频的动作说明「音频在 X 上」。
- 录音中的那一场：录完才出现在其他设备上。

## 6. 分步

1. `vt-sync` 包：设备身份、设备组、配对码、端点、连接管理、文档同步协议；用假文档在
   进程内测（不走中继、不开 mDNS）。
2. 同步文档与物化器：`library`、`recording/<id>`；本机改动写入同步文档的钩子；两个核心
   在同一进程里互相同步的集成测试。
3. 既有文档的同步：录音笔记、主题笔记、精修稿（只由录音那台投影）。
4. 核心接口与界面：设置 › 设备、配对流程、录音来源标注。
5. 中继门禁调整与部署；「音频不外传」门禁扩展到 `vt-sync`。

## 7. 音频不外传

`vt-sync` 在依赖图上够不到 `vt-audio` 与 `vt-crypto` 的音频接口；同步文档的字段是封闭
列表，没有音频、音频路径、密钥引用。`scripts/test_share_no_audio_gate.sh` 扩展到这个包。

## 8. 第二期：协作主题

- **一个主题一个空间。** 引擎在同一个端点上跑多个空间，握手带空间号；设备组是一个空间，
  每个共享出去的主题各是一个空间（`SpaceKind::Topic { notebook, owner }`）。主题空间里
  只有这个主题的文档、归属于它的录音（含转录、订正、笔记、标记）与名单；别的主题、未归入
  主题、内部笔记本（`__zutalk_internal_` 前缀）一概不出去。发出去之前按空间过滤，收进来
  时再查一遍：不属于这个主题的录音直接拒收。
- **邀请码只带用途。** 同一种码三种用途（加 Mac / 协作主题 / 备份机）；码本身只有
  地址、用途和一次性密钥，主题 id 与标题留在发起人那边，配对成功时才回传给加入方。
  粘贴的地方不分：设置 › 设备的输入框和主题列表的「加入协作」都认两种码，按用途分流；
  协作码加入后直接打开那个主题。
- **发起人与协作者。** 发起的那台是发起人：只有它能发邀请码、移出人、停止协作（核心拒绝
  时返回 `sync.error.not_owner`）。发起人自己的其他 Mac 经设备组照常拿到这个主题，不需要
  单独加入。协作者的改动先到发起人，再经设备组到发起人的其他 Mac。
- **移出与退出。** 和移除自己的 Mac 一样：先把名单改动送到对方，再断开；名单上的移除是
  永久的。被移出的一方留着已经同步到的内容，界面提示「你已被移出」。协作者退出、发起人
  停止协作之后，本机撤掉这个空间，主题留下成为普通主题。
- **删除共享主题。** 删除之前先退出协作（发起人删则先停止协作），删除只在本机和自己的设备
  组里生效，不会删掉别人手里的那份。
- **界面。** 主题卡片右键菜单与主题页标题旁的菜单多一项「协作…」：说明、生成邀请码（复制、
  倒计时）、参与的人（在线/上次同步，发起人可移出）、停止协作或退出。主题列表右上角有
  「加入协作」。
- **测试。** `library_sync` 的集成测试覆盖：只拿到被邀请的那个主题、改动经发起人传到其
  其他 Mac、协作者删主题不影响发起人、被移出的一方知道、发起人删主题后协作者留着副本。

## 9. 第三期：附近（同一网络，不经服务器）

两件事：把一场录好的录音的文字稿**递给**附近的一台 ZuTalk；让附近的 ZuTalk **直接看**
正在录的这一场的实时字幕。都走设备同步的同一个端点（第三条协议 `zutalk/nearby/1`），
不经字幕服务器；音频不在里面（「音频不外传」门禁第 5 层同时扫 `nearby_share.rs`）。
直连优先；会场 Wi-Fi 隔离了设备、直连打不通时，iroh 会退到自建中继转发密文（中继看不懂，
与设备同步跨网时一样）。

- **看见谁。** 本机愿意被看见时（打开了「接收」，或正在附近直播），把名字和状态放进
  mDNS 广播的自定义数据：`zt1|<r/l>|<名字>|<直播标题>`，iroh 限 245 字节，名字最多 64
  字节、标题填满剩下的，按字符截断。不愿意被看见时广播里只有匿名端点 id，和只开同步时
  一样。附近的名单来自 mDNS 的发现事件（对方改了广播内容会再报一次），没有回调，界面
  开着同步时两秒问一次（只读内存）。名字是对方自报的，只拿来提示。
- **递。** 发送方连上对方，先报标题和大小；对方的用户在提示框里点「接收」才开始传
  （两分钟没回答算没人接）。传的是这场录音的同步文档（主题与回收站清空，当一份副本）加
  录音笔记，JSON 里 base64，上限 64 MiB。收下时像收到自己另一台 Mac 同步来的录音一样
  物化，放进「未归入主题」，标注「来自 X」（X 存在 `sync_state` 的 `nearby_name/<id>`）。
  三条收件规矩：只收它自己说的那一场；来源设备必须是递稿的这台（QUIC 已认证）；本机已经
  有这场录音（或墓碑）就不收，陌生人不能借递稿改写本机已有的录音。收下的录音照常进自己
  的设备组。提示里的标题用发送方列表里显示的名字（没起标题的录音是开头的话）。
- **直播。** 和加密链接同一份线上形态（`link_share` 的实时帧与转录稿片）；QUIC 本身端到端
  加密，不再加一层。字幕出口（采集回调派发线程）同时喂链接与附近；转录稿由一条后台线程
  有人在看时每两秒重算，只把变了的片换成新的 `Arc`，观众只收到变了的片。晚到的观众先拿到
  全部片与最后一帧。主播关掉或录音结束（界面连续两拍看到录音已停）即散场，观众看到「已经
  结束」，字幕留在窗里；观看端什么也不落盘。和链接互相独立，可以只开一个。
- **界面。** 设置 › 设备 的「附近」卡片：「接收附近递来的转录稿」开关与此刻看得见谁。
  共享录音面板多一节「递给附近的 Mac」。直播面板底下多一个「同一网络的 ZuTalk 也能看」。
  附近有人在直播时，「开始录音」页最上面出现「附近正在直播」，点「观看」打开单独的
  「附近的直播」窗口（可切原文/各译文，关窗即离开）。递稿请求的提示框挂在最上层的表单上
  —— 挂在主窗口上会排在已经打开的表单后面，发送方那边等到超时。
- **测试。** vt-sync `tests/nearby.rs`（递稿要对方接收、拒绝/没开接收不落地、直播先补片再
  推帧再散场）与 mDNS 广播的编码；vt-ffi `library_sync` 三个集成测试（落进未归入主题并
  带笔记与标记、重复递稿不覆盖、拒绝不留痕、观看端读得懂链接的线上形态）。两台开发实例
  开着真实 mDNS 联调：发现、递稿、观看、散场都走通。
