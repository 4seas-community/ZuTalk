# 录音中的呈现层

录音进行时，界面怎样把 Rust 核心送来的行、译文和预览画到录音页和字幕浮窗上。本文覆盖 Swift 一侧从「收到回调」到「上屏」的全部路径；Rust 核心、Soniox 连接、时间线投影见 `timeline-projection.md`。

## 为什么重做

外部反馈：三语（泰、中、英）录音，「一翻译泰语就容易延迟，然后要关掉重启」。

量出来的事实：

- **Rust 核心是干净的。** 真 Soniox、邀请通道、10 分钟泰中英混讲重放：三条车道都是 1.00x，零重连，三栏译文 100% 落行，停止 0.4 s。
- **慢的是主线程，而且随录音时长线性变慢。** 把真页面挂在屏外窗口、文件当声源、走真 Soniox 测 30 分钟：主线程应答 p95 从 3.7 ms 线性涨到 130 ms；29 分钟时每 30 秒有约 50 次超过 100 ms 的停顿，那时只有 136 行。
- **采样定位**（`sample` 抓测试进程主线程）：增长的全是 SwiftUI 的逐行例行更新。LazyVStack 会留住建过的每一行，跟随直播沿又会把每一行都建出来，于是每次刷新都要把整场的行过一遍：逐行比较输入（行数组带全文，泰文、中文走慢速比较路径），逐行重跑观察跟踪。视图本身的求值是常数，涨的是逐行的簿记。
- **两个「累加」的设计错误互相放大。**
  - 页面每次刷新的工作量与整场长度成正比（上一条）。
  - 字幕浮窗的逐字显现每个计时器 tick 固定推进 33 ms。计时器跑在主线程上，主线程一忙 tick 就晚到，可仍按 33 ms 计，显现速度按「落后倍数」打折，积压一路涨到截断上限。泰文还被当成中文那样的密集文字，每秒只放 13 个字形，低于泰文到达的速度。

  两者形成闭环：页面越慢，tick 越晚；显现越慢，积压越多；卡片越长，排版越贵，页面又更慢。重启能好，是因为它清空了累加的状态。
- **泰文排版本身就贵。** 同长度下，CoreText 排泰文是中文的 4–6 倍、英文的 7–10 倍：468 个字 1.3 ms，1872 个字 5.5 ms。

## 四条规矩

1. **每帧工作量只与变化量有关，与录音时长无关。** 定稿的行冻结成不可变的块，每帧只碰在变的尾巴。
2. **只画最新状态，限速发布。** 一帧最多发布一次（页面 10 Hz）；主线程忙时丢帧不丢数据，延迟不累积。
3. **显现由时间推导，不由 tick 累加。** 每个显现单位到达时就排好到期时刻，画面只问「此刻哪些已到期」；任何一步都不晚于「到达 + 延迟上限」。
4. **文字工作只做一次。** 行投影（裁剪各栏文字等）按行缓存，行不变就不重算；按语言选显现单位和速率。

## 模块

### 时间线 `Capture/LiveTranscriptTimeline.swift`

- `TranscriptChunk`：序号 `sequence / 16` 相同的行为一块。块带 `id` 和 `version`，相等只比这两个整数；同时带全块的派生事实（最大开始、最大结束、最大和最小可编辑修订号），消费者不必再逐行扫。
- `LiveTranscriptTimeline`：store 改行时只调 `noteDurableChanged(sequences:)` 标记哪些块脏了（不知道范围就传 `nil`，按块逐一比对重建）；预览变了调 `notePreviewChanged()`。最多每 100 ms 重建脏块一次，发布一个 `LiveTranscriptFrame`。预览按块叠加，规则与 `NotebookCaptureLivePresentation.utterances` 完全相同（实现就是逐块调用它），所以分块结果与扁平合并逐行一致（有随机性质测试）。
- 「最新状态」由 `Source` 闭包在重建时读取，标记脏块不复制任何东西。

### 回调派发器 `Capture/CaptureClient.swift`、`Capture/CaptureContracts.swift`

- 原来派发器只留最新一个事件。主线程来不及取时，中间的增量连同它们带的行一起被丢掉，store 发现修订号断档，就从 Rust 重拉整场快照，再在主线程上整份替换。录一场真实的泰中英会议，3837 个事件里有 319 处断档：每处都是一次 O(整场) 的修复，而且主线程越慢，断档越多。
- 现在派发器保留排队的全部事件，主线程取的时候映射一次，用 `NotebookCaptureEventDTO.coalescing(_:into:)` 合并成一个事件交给 store。合并后的事件带 `coversFromRevision`：store 只要已经应用到它的前一个修订号，就不算断档。
- 合并与逐条应用严格等价，有随机性质测试：
  - 行：修订号高的胜，平局后到的胜；
  - 先被撤回、后又送回的行，两个列表里都留着（store 先删后加，删除会重置比较）；
  - 译文：撤回总是删除，撤回之后的最好一条再加回；
  - 全量快照覆盖它之前的一切。
- 排队超过 512 个事件时丢掉最老的，交给原有的断档修复兜底。
- Rust 端的回调邮箱（`crates/vt-ffi/src/notebook_capture_api.rs` 的 `coalesce_capture_events`）也照同样的规则合并，事件带 `covers_from_revision`。单靠 Swift 一侧合并，真录音 3 分钟仍有 12 处断档，每处正好跳过一个修订号：工作线程把上一个事件交给 Swift 的时候，邮箱里的那个被新的覆盖了。两层都合并以后，同样 3 分钟 1948 个事件、114 个由合并而来、0 处断档、0 次整场修复。
- 例外：一个修订号已经分配、却因刷新失败或派发器关闭而没有入队时，邮箱记下「连续性已断」，下一个事件不与排队的合并。客户端照旧看到断档并重新加载，这正是那个修订号存在的目的。

### Store 的改动 `Capture/ActiveBilingualTranscriptStore.swift`

- `utterances` 和 `translationCues` 不再是 `@Published`。它们几乎随每个事件变化，原来每变一次就让观察整个 store 的页面重读全文。现在只通知时间线；store 自身的状态字段照旧只在值变化时发布。
- 合并原地进行，只比较触及的行。原来是整份复制再整份比较，每个事件都是 O(整场)。
- 译文字典原地修改。原来每条 cue 赋值一次，每次都整表比较并重建索引；中间一版改成「复制一份改完再赋回」，结果每个事件仍复制整场的 cue。
- 「全场最高的可编辑修订号」原来是一个每次行变化都会失效的缓存，几乎每个事件都要整场重扫一遍；现在随合并增量维护，只有持有最大值的行被替换成更低的值时才重算一次。
- `continuationCueIndex`（空格旁边「译文在上一行/下一行」用的索引）最多每秒重建一次，并记下相对上一版「从哪个时间点开始有变化」（`unchangedBeforeMs`）。一个块的标记只读取开始于「块末 + 1 s」之前的片段，变化点在那之后，块就不用重算。
- 字幕浮窗的受众候选行（`audienceDurableCandidates` + `inheritedSourceAnchors`）原来每有一行变化就从第一行重扫。它是一个左折叠，现在由 `AudienceCandidateFold` 在每个块边界存检查点，哪块脏了就从前一块的检查点接着折叠；借用「上一个已识别语言」的块会被单独标出，那个语言变了才从它重算。结果与整场重扫逐项相同（有随机性质测试，含从中途检查点恢复）。

### 录音页 `Pages/NotebookTranscriptRowBlocks.swift`、`Pages/NotebookRealtimeUtteranceViews.swift`

- 活动录音的行只来自时间线的帧（`NotebookRealtimeActiveRunView` 观察 `timeline`）；历史录音的行由 `NotebookTranscriptRowCache.chunks(for:)` 切成块，块内容不变就沿用原来的块。
- 一块一个视图（`NotebookMultilingualRowBlock` / `NotebookTranscriptionRowBlock`，用 `.equatable()`），按块 id + 版本比较。行视图的闭包统一放进 `NotebookTranscriptRowActions`，不再参与比较。闭包永远不相等，原来会让 SwiftUI 把每一行都判为「变了」。
- 每块记住它构建时的上下文，并且只记会改变这一块的那部分：
  - 翻译进度截到「块末 + 绑定宽限 8 s」；
  - 可编辑修订号截到块内最大值；
  - 断档线、上一块最后的说话人、说话人名字的版本（`speakerNamesRevision`）；
  - 译文索引：按上面 `unchangedBeforeMs` 的规则判断。

  直播沿走过之后，老块的上下文不再变，也就永远不再重建。
- 截断是等价变换，有测试逐个对照：可编辑判定与未截断时相同，「等待中」的判定与未截断时相同。

### 字幕浮窗 `WindowSystem/Surfaces/CaptionReveal.swift`

- `CaptionScriptProfile`：每种文字一份配置，规定显现单位、速率和延迟上限。
  - 拉丁文：按空格分词，每秒 9 步。
  - 中文、日文：按字形，每秒 18 步，标点自成一步。
  - 泰文：用 `CFStringTokenizer` 按词典切词，每秒 8 步；切点对齐到字形边界，元音符号和声调符号永远跟着它的辅音。
  - 韩文：按空格分隔的语节，每秒 7 步。
  - 延迟上限都是 1.2 s。
  - 优先按栏的语言选配置，没有语言时按文字的脚本判断。
- `CaptionRevealPlan`：纯数据。文字更新时，没变的步保留原来的时刻表，看过的字不会重放；待显现的步从当前时刻起，在 `min(步数 / 速率, 延迟上限)` 内均匀铺开，并逐步截到「到达 + 延迟上限」。
- `AudiencePacedText`：用 `TimelineView(.animation)` 按屏幕刷新取当前时刻画 `visibleText(at:)`；最后一步到期后切回静态文字，不再占用帧。全程没有累加状态。

## 语言特例汇总

| 语言 | 问题 | 处理 |
|---|---|---|
| 泰语 | 不写空格；元音、声调是组合附标；按词典断行，排版贵；Soniox 对泰语长段很少断句（一行 20–25 s） | 显现按分词器切出的词；单独一档速率；行投影缓存避免反复裁剪；长行只在最后一块里重排 |
| 中文、日文 | 字密，标点是天然停顿 | 按字显现，标点单独一步 |
| 英文等 | 按词阅读 | 按词显现 |
| 韩文 | 空格分隔语节 | 按语节显现 |

- `ZuTalkTests/LiveCaptureReplayTests.swift`
  - `LiveCaptureReplayTests`：真页面 + 真核心 + 真 Soniox。用文件当声源，屏外窗口里挂上录音页和浮窗，每 30 秒报告主线程应答分位数和页面落后音频的秒数；可以把核心送来的全部回调录成 JSONL（`record`）。
  - `LiveCaptureOfflineReplayTests`：把录下的回调流按倍速重放进同样的页面和浮窗。核心在底下做一场不连网的本地录音，提供真实的会话和历史记录；断档修复要查的快照，由重放客户端按已送出的事件回答。报告主线程分位数，以及回调按时刻表应到、实际送达的差值（即字幕被主线程耽误了多久）。

## 结果

同一份真实录制（泰中英，`--coalesced` 拼成两小时）离线重放，32 倍速加压，录音页三栏 + 字幕浮窗，Debug 构建：

| 录音量 | 旧版主线程 p95 | 旧版送达延迟 p95 | 新版主线程 p95 | 新版送达延迟 p95 |
|---|---|---|---|---|
| 0–5 分 | 10.6 ms | 10.5 ms | 7.0 ms | 5.2 ms |
| 30–35 分 | 65.7 ms | 60.7 ms | 8.0 ms | 6.8 ms |
| 55–60 分 | 95.2 ms | 94.7 ms | 2.4 ms | 6.6 ms |
| 115–120 分 | — | — | 7.6 ms | 5.7 ms |

旧版用的是带断档的原始录制（断档正是旧派发器造成的）。新版两小时 404 行，主线程与送达延迟都不随时长增长；送达延迟的中位数始终约 1 ms。

真 Soniox、1 倍速、6 分钟：主线程 p95 随语料内容在 4–20 ms 之间起伏（长泰文段落时高，换语言后回落），不随时长上升；断档修复 0 次。

## 没做的

- Release 构建的实测。
- 页面上正在增长的泰文长行，仍然整段重排（在最后一块里）。等 Release 构建实测后再决定要不要切段。
- Rust 端每条辅助 partial 都发一个持久增量，事件频率约 12 次/秒。Swift 这一侧已经不再按事件付出整场的代价；要不要在 Rust 端合并，留给有数据之后再定。
